## Summary

「RAGを応用したTodo更新」でクラスタに意味を持たせるには，30秒から数分の区間を単なるテキスト断片又は時系列スコア列として保存しない方がよい．区間ごとに，作業内容を説明するテキスト，成果物差分，画面・操作イベント，EEG由来スコアの時系列，ユーザの承認・拒否・次回結果をまとめた「状態エピソード」を作り，そのエピソードをグラフのノードとして扱う．

ここで重要なのは，時系列に並んだ指標そのものは意味を持たない，という点である．たとえば，認知負荷が高く操作量が低い区間は，「高負荷で停滞」かもしれないし，「低活動だが思考中」かもしれない．両者を分けるには，画面内容，成果物差分，Todoの完了条件，直前直後の操作，ユーザ訂正を合わせて，区間に意味ラベルを付ける必要がある．

理想的な単位データは，次の3層を同時に持つ．

1. 検索用テキスト: その区間で何をしていたか，何が詰まりか，何が進んだかを自然言語で要約する．
2. 時系列スコア: 集中力，認知負荷，接近/回避，低覚醒，操作量，成果物変化を，数秒から15秒程度のサンプル列として保存する．
3. グラフ用関係: 前後の時間接続，Todo・成果物・アプリ・介入・結果への接続，意味類似エッジ，状態遷移パターンのエッジを分けて保存する．

結論として，RAGの検索単位は「区間テキスト」ではなく，`StateEpisode + StateEvidence + StateMeaning + TransitionLinks + Outcome` の複合レコードにする．クラスタリングや近傍検索では，テキスト埋め込みだけでなく，時系列から作った特徴量ベクトルと，区間に付与された意味ラベルを併用する．生の時系列は後から再解析できるように残し，クラスタには平均値だけでなく，傾き，変動，ピーク，状態遷移，進捗差分，作業文脈を反映させる．

「停滞から回復へ向かった経路」は，この一般的な状態遷移の一例である．同じ仕組みで，「順調な集中から離脱」「高負荷な集中から停滞」「離脱から復帰」「低活動だが思考中から成果物更新」なども扱える必要がある．そのため，エピソード単体に回復専用の項目を増やすのではなく，すべての状態に共通する意味付けと遷移記述を持たせる．

## このフォーマットで管理すべき状態

`nedo/drafts/脳波ポモドーロ_提案書_0620.txt` が想定している主状態は，少なくとも次である．

| 状態 | 主な条件 | 意味 | Todo更新への使い方 |
| --- | --- | --- | --- |
| 順調な集中 | 操作量が高く，認知負荷が低又は適正で，進捗がある | 現在のTodo粒度と作業条件が合っている | 現状のTodo設定方針を維持する |
| 高負荷な集中 / 高負荷だが進捗あり | 操作量が高く，認知負荷も高く，成果物差分又は完了条件の前進がある | 難しいが前に進んでいる | 次回の作業単位を少し小さくする，休憩又は低負荷タスクを挟む |
| 高負荷で停滞 | 認知負荷が高く，進捗がなく，同じ操作やエラーが反復する | 試行錯誤しているが前に進んでいない | 調査，判断，作成，確認を分け，最初の一手を提示する |
| 低活動だが思考中 | 操作量は低いが，画面注視，関連資料表示，高め又は適正な負荷，直後の進捗がある | 手は止まっているが作業は継続している | 介入を抑制し，深い思考を保護する |
| 作業からの離脱 | 操作量が低く，負荷又は課題関与が低く，対象Todoとの関連が薄い画面へ移っている | 注意が対象作業から外れている | 休憩，復帰用の小タスク，一日の残りタスク再評価を提案する |
| 未着手 | 対象Todoの画面又は成果物が開かれておらず，完了条件にも変化がない | まだ作業が始まっていない | 対象ファイルを開く等の着手行動を提示する |
| 中断 / 切替 | 通知，アプリ切替，会議，別Todoへの移動がある | 外的又は内的な文脈切替が起きた | 復帰時に前の文脈と次の一手を提示する |

これらは単一の指標値ではなく，次の組み合わせで決まる．

- 生理スコア: 認知負荷，課題関与，低覚醒，接近/回避，品質マスク．
- 行動スコア: 操作量，アイドル時間，アプリ切替，反復操作，対象Todoとの関連度．
- 成果スコア: 成果物差分，完了条件達成度，進捗差分．
- 画面意味: 画面内容テキスト，OCR/VLM要約，エラー表示，資料閲覧，対象ファイル，対象URL．
- 文脈: Todo，親Todo，作業種別，直前状態，直後状態，休憩，中断．
- ユーザ訂正: 「考えていた」「離脱していた」「この提案は役に立った」等の後付けラベル．

## 概念フォーマット

初期段階では，JSONのような実装形式よりも，「人間が読める記録票」として次の単位を崩さないことが重要である．

### 1区間の記録票

1区間は，30秒から数分の「意味を持つ作業状態」である．単なる5秒ごとのスコア列ではなく，スコア列，画面内容，成果物差分を合わせて，「この区間は何だったのか」まで書く．

| 項目 | 記録する内容 | 目的 |
| --- | --- | --- |
| 時刻 | 開始時刻，終了時刻，長さ | 前後の区間とつなぐため |
| 対象Todo | 親Todo，今回のTodo，完了条件，作業種別 | 何のための作業だったかを示すため |
| 画面内容テキスト | 表示アプリ，ウィンドウ名，開いているファイルやURL，OCR/VLM要約，画面上のエラーや資料 | スコア変化の原因を作業文脈として説明するため |
| 成果物差分 | どのファイルや文書がどう変わったか，完了条件がどれだけ進んだか | 進捗の有無を脳波ではなく成果から見るため |
| 操作の特徴 | キー入力，マウス，スクロール，アイドル，アプリ切替，同じ操作の反復 | 手が動いていたか，止まっていたか，迷っていたかを見るため |
| EEG/生理スコア列 | 認知負荷，課題関与，接近/回避，低覚醒，品質マスクの時系列 | 内的状態の変化を後から再計算できるようにするため |
| スコア列の要約 | 負荷の高低，負荷の上昇/下降，操作量の高低，集中指標の高低，進捗差分 | 生の時系列を状態判定に使える特徴へ変換するため |
| 状態の意味 | 順調な集中，高負荷な集中，高負荷で停滞，低活動だが思考中，離脱，未着手，中断/切替など | 「この区間は何だったのか」を検索可能にするため |
| 判定理由 | なぜその状態と見なしたか，反対証拠は何か | 誤判定を後から直せるようにするため |
| ユーザ訂正 | ユーザが「これは考えていた」「これは離脱だった」等と直した内容 | 個人化とラベル品質向上のため |
| 介入・提案 | この区間で提示した休憩，タスク分解，切替提案，Todo案 | どの支援が状態変化に関係したかを見るため |
| 検索用テキスト | 画面内容，状態意味，進捗，提案を短くまとめた文章 | RAGで取り出す単位にするため |

### 記録例

| 項目 | 例 |
| --- | --- |
| 時刻 | 10:15:00-10:17:30 |
| 対象Todo | NEDO提案書のRAG節を整理する |
| 画面内容テキスト | VS Codeで提案書下書きと設計メモを表示．RAGのデータ形式について書いている．ブラウザにはEventRAGのページが開いている． |
| 成果物差分 | 設計メモに「状態エピソード」と「状態遷移」の説明を追加した． |
| 操作の特徴 | キー入力は多い．同じ段落の書き直しが少しある．アプリ切替は少ない． |
| EEG/生理スコア列 | 認知負荷は中から高へ上昇．課題関与は中から高．接近/回避は大きな変化なし． |
| スコア列の要約 | 高負荷だが操作量と成果物差分がある． |
| 状態の意味 | 高負荷な集中 / 高負荷だが進捗あり |
| 判定理由 | 負荷は高いが，対象ファイルに意味のある追記があり，画面も対象Todoに直接関係しているため． |
| ユーザ訂正 | なし |
| 介入・提案 | なし |
| 検索用テキスト | RAG節のデータ形式設計で高負荷だったが，状態エピソードと状態遷移へ分ける方針を追記して前進した． |

### 複数区間の遷移記録票

状態の意味は1区間だけでは決まらないことがある．たとえば「低活動だが思考中」は，その直後に成果物差分が出て初めて確からしくなる場合がある．そのため，隣り合う複数区間をまとめて「状態遷移」として記録する．

| 項目 | 記録する内容 | 目的 |
| --- | --- | --- |
| 遷移の範囲 | 起点区間，終点区間，途中区間 | どの区間列を一つの遷移として見るかを示す |
| 起点状態 | 例: 高負荷で停滞，順調な集中，低活動だが思考中 | どの状態から始まったかを示す |
| 終点状態 | 例: 順調な集中，離脱，成果物更新，未着手 | どの状態へ移ったかを示す |
| 遷移名 | `高負荷で停滞 → 順調な集中`，`順調な集中 → 離脱` など | クラスタや検索で扱う名前にする |
| きっかけ | 通知，休憩，タスク分解，資料閲覧，エラー解消，ユーザ介入なし等 | 状態が変わった要因候補を保存する |
| 変化した指標 | 負荷低下，操作量増加，進捗増加，課題関与低下など | 遷移を時系列データで裏づける |
| 画面・成果物の変化 | どの画面からどの画面へ移ったか，何が更新されたか | 遷移を作業文脈で説明する |
| Todoへの意味 | 維持すべきか，細分化すべきか，休憩すべきか，復帰用タスクを作るべきか | Todo更新へ接続する |
| 検索用テキスト | 遷移全体を短く説明する文章 | RAGで「似た遷移」を取るため |

### 遷移記録例

| 項目 | 例 |
| --- | --- |
| 遷移の範囲 | 10:12:00-10:17:30の3区間 |
| 起点状態 | 高負荷で停滞 |
| 終点状態 | 高負荷だが進捗あり |
| 遷移名 | 高負荷で停滞 → 高負荷だが進捗あり |
| きっかけ | 「保存単位」と「検索単位」を分ける方針に切り替えた |
| 変化した指標 | 認知負荷は高いままだが，操作量と成果物差分が増えた |
| 画面・成果物の変化 | 同じ設計メモ内で，回復専用設計から状態一般の設計へ書き換えた |
| Todoへの意味 | 次回も，詰まったら設計対象を「状態」と「遷移」に分けて考えるとよい |
| 検索用テキスト | 高負荷で停滞していたが，概念を保存単位と検索単位に分けたことで，高負荷のまま前進した． |

この形式では，時系列スコアは保存するが，それ自体を意味とはみなさない．スコア列は，画面内容テキスト，成果物差分，Todo文脈と合わせて，状態意味と状態遷移へ変換してから検索する．

## 先行研究から見た設計上の要点

### 1. 個人情報記録は collection, integration, reflection, action まで設計する必要がある

Li, Dey, and Forlizzi (2010) の personal informatics モデルは，個人データ活用を preparation, collection, integration, reflection, action の段階として整理している．本システムに当てはめると，画面録画やEEGを集めるだけでは不足であり，後から振り返り，Todo更新という action に接続できる形へ統合して保存する必要がある．

したがって，区間データには「記録値」だけでなく，「その区間から次に何を変えたか」「提案をユーザが承認したか」「次回に改善したか」を含める必要がある．

### 2. ScreenTrackは画面履歴が作業文脈の復帰に有効であることを示す

ScreenTrack (Hu and Lee, 2020) は，一定間隔で取得したPC画面の視覚的履歴を用いて，過去に開いた文書やWebページへ戻る支援を行った．本提案では，画面配信を単に保存するのではなく，区間の代表フレーム，OCR/VLM要約，表示アプリ，ファイルパス，URL，Todoとの対応をエピソードに紐づける．

これにより，「高負荷だった」というスコアだけでなく，「どの画面・どの成果物・どのエラー・どの資料が高負荷区間に対応したか」を復元できる．

### 3. EventRAGや時間付きGraphRAGは，時間順序を通常のベクトル検索から分離して保持する

EventRAG (Yang et al., 2025) は，イベント知識グラフを用いて，物語的・時間的な関係を含む検索生成を改善する．通常のRAGは意味的に近い断片を返せるが，前後関係や「停滞から回復へ向かった経路」は保持しにくい．

本提案では，エピソード間に少なくとも次のエッジを分けて持つ．

- `NEXT`: 実際の時系列で次に起きた区間．
- `PREVIOUS`: 実際の時系列で直前の区間．
- `SAME_TODO`: 同じTodo又は親Todoに属する区間．
- `SAME_ARTIFACT`: 同じファイル，URL，アプリ，文書，コード領域に関係する区間．
- `SIMILAR_CONTEXT`: テキスト・画面・成果物差分が意味的に近い区間．
- `SIMILAR_TRAJECTORY`: 認知負荷や集中力の時系列形状が近い区間．
- `STATE_TRANSITION`: ある状態から別の状態へ移った区間列．例: `stuck_to_productive_focus`，`productive_focus_to_distraction`，`high_load_focus_to_stuck`．
- `TRANSITION_TRIGGER`: 状態遷移の直前に観測された画面変化，通知，介入，休憩，タスク分解，成果物更新．
- `TRANSITION_OUTCOME`: 遷移後に生じた進捗，完了，離脱，負荷低下，ユーザ承認又は拒否．
- `REGRESSED_TO`: 一度進んだ後に，過負荷，離脱，先送りへ戻った経路．

クラスタが意味を持つためには，`SIMILAR_CONTEXT` と `SIMILAR_TRAJECTORY` を混ぜすぎない．「同じ作業内容で詰まるクラスタ」と「違う作業でも同じ負荷パターンを示すクラスタ」は別のクラスタとして見える方が，Todo更新に使いやすい．

### 4. CPMSやMindMirrorは，仕事中の状態支援ではローカル保存，JSONログ，手動訂正が重要であることを示す

CPMS (Obiuwevwi et al., 2026) は，知識労働のエピソード想起を支援するため，発話，生理信号，視線を時間同期されたJSON形式のエピソード記録として保存する．MindMirror (Luo, Wang, and Wang, 2026) は，デジタルワーカー向けに状態確認，手動訂正，構造化内省，LLM提案，日次・週次レビューをつなぐローカルファースト設計を取る．

本提案でも，状態ラベルはシステムの推定だけで確定しない．ユーザが「これは離脱ではなく考えていた」「このTodo提案は役に立った」などを訂正できる欄を持つ．この訂正履歴が，RAG検索時の重み付けと後の個人化学習に効く．

## 時系列スコアをグラフとクラスタに効かせる方法

### 1. 生の時系列を保存し，検索用には要約特徴量を作る

周波数解析を含むEEG指標は，区間全体で1点に潰さない．`focus`，`cognitive_load`，`approach_avoidance` などは5秒又は15秒間隔の時系列として保存する．そのうえで，検索・クラスタリング用に次の要約特徴量を作る．

- 平均: 区間全体の状態水準．
- 傾き: 上昇中か，低下中か．
- 変動: 安定しているか，不安定か．
- 面積: 高負荷や低集中がどれだけ持続したか．
- ピーク: 一時的な高負荷又は急落の有無．
- 前後差分: 直前エピソードからどれだけ変化したか．
- 遷移: 低負荷から高負荷へ，高負荷から回復へ，などの状態変化．
- motif: `rising_load_no_progress`，`low_activity_high_focus`，`high_activity_high_load_progress` のような形状ラベル．

クラスタリングは，テキスト埋め込みだけで行うと「同じ話題」は集まるが，「同じ状態」や「同じ遷移」は集まりにくい．逆に時系列だけで行うと，画面内容やTodoの意味が落ちる．したがって，少なくとも次の4種類の近傍を別々に作る．

- 文脈近傍: `context_text`，画面要約，成果物差分要約から作る．
- 軌跡近傍: `series_summary` と時系列埋め込みから作る．
- 状態近傍: `state_meaning.primary_state`，状態候補，判定理由から作る．
- 遷移近傍: `transition_context.transition_label` と `StateTransition` から作る．
- 成果近傍: `outcome`，次回Todo受諾，後続エピソードの改善から作る．

### 2. クラスタは「作業内容」ではなく「Todo更新に使う問い」に合わせて作る

クラスタの目的は見た目の分類ではなく，次回Todoを良くすることである．そのため，クラスタは次の問いに対応させる．

- どの作業文脈で，負荷が上がりやすいか．
- 負荷が上がっても成果が出る作業と，停滞する作業は何が違うか．
- 低活動区間のうち，深い思考だったものと離脱だったものは何が違うか．
- どの介入又は次Todoが，後続エピソードの回復に結びついたか．
- どの時間帯，タスク粒度，前回休憩条件で，順調な集中へ入りやすいか．

この問いに答えるため，クラスタ名はLLMに自由生成させるだけではなく，構造化された条件から命名する．例:

- `writing_outline_high_load_recovers_after_subtasking`
- `coding_debug_repeated_error_high_activity_no_progress`
- `reading_low_activity_high_focus_no_intervention`
- `admin_task_low_load_high_completion`

### 3. 時間エッジをたどって「似ている現在」から「目的の状態」へ向かう経路を検索する

RAGでTodo更新を行うときは，現在の区間に似た過去区間を直接LLMへ渡すだけでは弱い．現在の状態をまず意味ラベルとして解釈し，その状態からどの状態へ移したいのかを決めた上で，過去の状態遷移を検索する．

1. 現在エピソードを，文脈近傍と軌跡近傍で検索する．
2. 取得した過去エピソードのうち，`state_meaning.primary_state` と `series_summary` が現在に近いものを起点候補にする．
3. 起点候補から `NEXT` エッジをNステップたどり，目的状態に近い終点候補を探す．目的状態は，現在が停滞なら `productive_focus` 又は `productive_high_load`，現在が離脱なら `thinking` 又は `productive_focus`，現在が高負荷な集中なら `lower_load_progress` のように設定する．
4. 起点と終点の間にある画面変化，成果物差分，操作変化，介入，休憩，タスク分解を `StateTransition` として保存する．
5. 検索時には，現在エピソードに似た `StateEpisode` だけでなく，その状態を起点に含む `StateTransition` を優先して取得する．
6. LLMには「似ていた過去」だけでなく，「どの状態から，何を変え，何分後にどの状態へ移ったか」を根拠として渡す．

この設計なら，「高負荷で停滞していた過去区間」と「その後に小さな調査Todoへ分けたら進んだ」という遷移だけでなく，「順調な集中から通知で離脱した」「低活動だが思考中のあとに成果物更新が生じた」「高負荷な集中が長く続いて停滞へ移った」といった遷移も検索できる．Todo更新は，単発の類似例ではなく，時系列上の状態遷移パターンに基づく提案になる．

### 4. 状態遷移のピックアップ条件

状態遷移は，主観的に良さそうな区間を後から眺めて選ぶのではなく，次の規則で機械的に候補抽出する．

起点は，次のいずれかを満たす区間とする．

- `state_meaning.primary_state` が確定又は高信頼度で付与された．
- `series_summary` に大きな変化があり，状態変化の起点になりうる．
- Todo，画面，成果物，アプリ，通知，休憩などの文脈が変わった．
- ユーザ訂正で「考えていた」「詰まった」「離脱していた」「戻れた」などが付与された．

終点は，起点からNステップ以内又は一定時間以内に現れ，次のいずれかを満たす区間とする．

- `state_meaning.primary_state` が起点と異なる状態へ変わった．
- `progress_delta`，`completion_delta`，`effective_activity`，`cognitive_load`，`engagement` のいずれかに意味ある変化が生じた．
- Todo更新案，タスク分解，休憩，切替のいずれかをユーザが承認又は拒否した．
- 後続ブロックでTodoが完了，部分完了，前進，停滞，離脱のいずれかとして確定した．
- ユーザが状態解釈又は提案に評価を付けた．

起点から終点までの遷移候補が複数ある場合は，次の順で優先する．

1. 状態ラベルの変化と，成果物差分又はTodo状態の変化が一致する遷移．
2. ユーザ訂正又はユーザ評価によって意味が確認された遷移．
3. 画面内容テキストに，エラー，通知，資料閲覧，作成完了などの明確な文脈変化がある遷移．
4. 現在エピソードと文脈近傍，軌跡近傍，状態近傍のいずれも近い遷移．
5. 同じ親Todo又は同じ成果物に属する遷移．

これにより，たとえば現在が「スライド作成で高負荷・進捗なし」の場合，システムは「過去に同じような高負荷停滞があり，作業を『構成だけ作る』に分解した後，2区間後に成果物差分が増えた」遷移を優先して取得できる．一方，現在が「低活動だが思考中」の場合は，介入で中断した経路ではなく，そのまま維持した後に成果物差分が増えた遷移を優先して取得できる．

## エピソード境界の決め方

### Option 1: 固定長区間

30秒，60秒，120秒などで機械的に切る．

利点: 実装が簡単で，サンプル数が揃う．

弱点: 状態変化の途中で切れる．意味のある作業単位と一致しにくい．

### Option 2: 変化点ベース区間

認知負荷，操作量，画面文脈，成果物差分の変化点を検出して切る．

利点: 「詰まり始めた」「復帰した」などの意味ある境界に近い．

弱点: 初期実装では変化点検出が不安定になりやすい．

### Option 3: ハイブリッド区間

内部処理は5秒から15秒の固定サンプルで行い，RAGノードは30秒以上の持続状態又は明確な変化点でまとめる．

利点: 時系列解析の安定性と，作業意味のまとまりを両立できる．

弱点: 境界決定のルールを明示して評価する必要がある．

### Recommendation

初期実装は Option 3 がよい．固定サンプルは解析の土台として保存し，グラフのノードは状態が30秒以上続く，画面文脈が変わる，成果物差分が生じる，介入が提示される，Todoが切り替わる，のいずれかで確定する．

## 最小実装で必要な保存項目

初期PoCでは，すべての時系列埋め込みやGraphRAGを実装しなくてもよい．ただし，将来のRAG/Todo更新に効くよう，次の項目だけは最初から保存する．

| 区分 | 保存項目 | 理由 |
| --- | --- | --- |
| 時間 | start, end, duration, previous_episode_id, next_episode_id | 時系列経路検索に必須 |
| Todo | todo_id, parent_todo_id, declared_goal, done_criteria | 類似タスクと未達成条件を検索するため |
| 画面 | app, window_title, URL/file path, OCR/VLM要約, representative frame id | 状態変化の原因説明に必要 |
| 成果物 | diff summary, changed file ids, progress_delta | 進捗の有無を脳波ではなく成果で判断するため |
| 操作 | effective_activity, idle_sec, app_switch_count, repeated_action_score | 思考，停滞，離脱を分けるため |
| EEG | focus, cognitive_load, approach_avoidance, fatigue/arousal, quality mask | 内的状態の時系列を残すため |
| 介入 | intervention type, content, timing | どの支援が効いたかを見るため |
| 結果 | next state, todo accepted/rejected, completion, user rating | 状態遷移が作業改善につながったかを評価するため |
| 状態意味 | primary state, state candidates, reason text, counter evidence, human correction | 指標列を「何の状態か」に変換するため |
| 状態遷移 | StateTransition, start/end condition, turning point, state change action, transition metrics | 複数エピソードにまたがる遷移パターンをRAGの取得単位にするため |

## 提案書へ入れる場合の短い表現案

> 本システムでは，作業履歴を単なる画面録画又はテキストログとして保存せず，30秒から数分ごとの状態エピソードとして構造化する．各エピソードは，タイムスタンプ，作業内容の自然言語要約，画面内容テキスト，成果物差分，操作ログ，脳波由来の集中力・認知負荷・接近/回避傾向の時系列，時系列要約，状態意味，介入内容及び後続結果を含む．さらに，複数エピソードをまたぐ状態変化を `StateTransition` として保存し，「高負荷で停滞から順調な集中」「順調な集中から離脱」「低活動だが思考中から成果物更新」等の遷移を検索可能にする．これにより，現在の状態と似た過去区間を検索するだけでなく，「どの状態から，何を変え，何分後にどの状態へ移ったか」を根拠として，次回Todoの分解・順序づけに反映する．

## 未解決点

- 何秒ごとの固定サンプルが最適かは，EEGの窓長，画面理解コスト，LLM呼び出し頻度の制約で決める必要がある．初期案は5秒又は15秒である．
- 接近/回避指標はFAAだけで確定せず，自己報告や行動結果との対応を見て探索的に扱う必要がある．
- クラスタリングの重みは，文脈，時系列，結果のどれを重くするかで大きく変わる．初期PoCでは，可視化用クラスタとTodo更新用検索を分ける方が安全である．
- 画面録画と成果物差分はプライバシー上のリスクが高いため，保存対象ウィンドウの限定，除外ルール，ローカル保存，削除可能性をデータ形式の一部として扱う必要がある．
